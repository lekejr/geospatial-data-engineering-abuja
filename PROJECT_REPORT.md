# Project Report: Geospatial Data Engineering Pipeline for Abuja, Nigeria

## 1. Purpose

This project was built to demonstrate practical data engineering skills
applied to geospatial data — specifically, the ability to take raw,
messy, real-world spatial data and turn it into clean, validated,
analysis-ready tables in a production-style spatial database. It
complements a broader portfolio in GIS, remote sensing, and geospatial
machine learning by addressing the data infrastructure layer that
underpins any spatial analysis: without a reliable pipeline, no
downstream analysis or model can be trusted.

The project scope was deliberately kept small and laptop-friendly. The
objective was not to build the largest or most complex system possible,
but to demonstrate correct, defensible data engineering fundamentals:
ingestion, validation, cleaning, transformation, database design, and
automated quality reporting.

## 2. Data Source and Scope

Data was sourced from **OpenStreetMap**, accessed via the OSMnx Python
library, which queries the Overpass API. Two datasets were pulled for a
bounding box covering central Abuja (Wuse, Garki, Maitama, Asokoro, and
the Central Business District):

- **Roads** — the drivable road network
- **Buildings** — all tagged building footprints

A bounding box was used instead of an administrative boundary after two
earlier approaches failed: querying the entire Federal Capital Territory
was too large a request for OSM's public Overpass server to reliably
return, and Abuja Municipal Area Council's administrative polygon did
not resolve cleanly through OSM's geocoder. The bounding box approach
gave predictable, reproducible results and direct control over the size
of the pulled dataset — a deliberate trade-off in favor of reliability
and reproducibility over full administrative coverage.

Two datasets were judged sufficient to demonstrate the full pipeline:
they provide two distinct geometry types (lines and polygons), two
distinct measurement operations (length and area), and one genuine
cross-dataset spatial question (building proximity to roads).

## 3. Methodology

The pipeline follows six stages:

1. **Ingestion** — raw data pulled from OSM and saved untouched to disk,
   preserving an unmodified copy for reference.
2. **Validation** — the raw data was inspected (not modified) for null
   geometries, invalid geometries, duplicate records, geometry type
   distribution, and coordinate reference system, to establish an
   honest baseline before any cleaning occurred.
3. **Cleaning** — invalid geometries were repaired, duplicate rows were
   removed, multi-value tag fields were flattened to single values,
   building geometries were standardized to a single consistent type,
   and the data was reprojected from geographic coordinates (EPSG:4326)
   to a metric coordinate system (EPSG:32632, UTM Zone 32N) suitable for
   measuring length and area.
4. **Loading** — cleaned data was loaded into a PostgreSQL/PostGIS
   database, into a `staging` schema with spatial (GIST) indexes on
   each geometry column.
5. **Transformation** — SQL and PostGIS spatial functions were used to
   build an `analytics` schema: summary tables grouped by road and
   building type, and a spatial join calculating each building's
   distance to the nearest road.
6. **Quality Reporting** — a script queries the raw files, cleaned
   files, and live database directly to produce a data quality report,
   ensuring every reported number is generated by code rather than
   entered by hand.

The database was run via Docker to ensure the environment is
reproducible on any machine, without requiring a manual PostGIS
installation.

## 4. Data Quality Summary

| Dataset | Raw Records | After Cleaning | Loaded to Database |
|---|---|---|---|
| Roads | 26,111 | 26,111 | 26,111 |
| Buildings | 61,854 | 61,847 | 61,847 |

The raw road data contained zero null geometries, zero invalid
geometries, and zero duplicate records. The raw building data contained
seven records with Point-only geometries (no polygon outline), which
were removed during cleaning since they could not produce a valid area
measurement. No other records required removal.

## 5. Results

- **26,111** road segments were mapped, totalling approximately
  **3,494 km** of road length within the study area, across 13 distinct
  road classifications.
- Residential roads account for the largest share of total length
  (approximately 2,402 km), consistent with a dense urban residential
  street network.
- **61,847** building footprints were mapped, totalling approximately
  **14.9 million m²** of building area.
- **97.8%** of buildings (60,511 of 61,847) are located within 200
  metres of a mapped road, indicating strong overall road coverage
  relative to the built environment in this area.
- The majority of buildings (60,274 of 61,847) carry only the generic
  `building=yes` OSM tag rather than a specific subtype — a known,
  common characteristic of crowd-sourced OSM data reflecting how
  contributors tag features, not a data quality failure introduced by
  this pipeline.

## 6. Technical Decisions Worth Highlighting

- **Spatial indexing**: GIST indexes were added to both staging tables
  specifically because the analytics layer performs a proximity join
  between roads and buildings — without indexing, this comparison would
  require a full scan across tens of thousands of geometries for every
  comparison.
- **Two-stage proximity logic**: the building-to-road proximity
  calculation first uses `ST_DWithin` at a wider radius (200m) to
  generate an index-assisted candidate set, then calculates exact
  distance only within that smaller set — a standard pattern for
  keeping spatial joins performant at scale.
- **Multi-value tag handling**: OSM tag fields that can hold multiple
  values per feature appeared in three different forms depending on the
  data's read path (Python list, NumPy array, or a GeoJSON-serialized
  string). All three needed explicit handling to avoid corrupting
  downstream category labels — a concrete example of a subtle but real
  data engineering problem.

## 7. Limitations

- The study area is a bounding box over central Abuja, not the full
  Federal Capital Territory — a deliberate scope decision for
  reproducibility, not full administrative coverage.
- Data quality reflects OpenStreetMap's crowd-sourced nature; subtype
  tagging in particular is inconsistent.
- Proximity is measured as straight-line distance, not travel distance
  along the actual road network.
- No formal automated test suite is included; data quality is verified
  through dedicated validation and reporting scripts rather than a
  testing framework such as pytest or Great Expectations.

## 8. Conclusion

This project demonstrates a complete, reproducible data engineering
pipeline for geospatial infrastructure data: from raw acquisition
through validation, cleaning, spatial transformation, database loading,
and automated quality reporting. Every stage produces verifiable,
code-generated evidence of its own correctness — record counts,
geometry checks, and coverage statistics — rather than assumed or
manually asserted results. The full pipeline, source code, and
documentation are available in the linked repository.
